# Design — Brass Editorial UI: React foundation + report re-skin

**Date:** 2026-06-03
**Status:** Approved direction; Phase 1 ready for implementation planning
**Supersedes:** the indigo "Modern SaaS" uplift on branch `feat/ui-ux-uplift` (this
session, uncommitted) — that visual direction is replaced by Brass Editorial.

---

## 1. Context

The posture-assessment product has three stakeholder-facing HTML deliverables —
the **questionnaire** (facilitator instrument), the **matrix viewer** (vendor /
current-state / compliance report), and the **executive summary** (board print
view). All are generated, self-contained, offline single files.

Earlier this session they were re-skinned to an indigo "Modern SaaS" look. The user
redirected: they want (a) a more distinctive, premium aesthetic, (b) the whole
engagement to **start from the UI** (a facilitator opens one offline link and works
end-to-end), and (c) a new ability to **attach client evidence** to use cases.

Through interactive mockups (visual companion), the following were chosen:

- **Aesthetic:** *Brass Editorial × Technical* — one type system, two themes.
- **Build:** **React + Tailwind**, bundled to a single offline `.html` (Vite +
  `vite-plugin-singlefile`).
- **UI scope:** *Middle* — launcher + questionnaire + evidence live in the browser;
  matrix/exec stay Python-generated but are reached/triggered from the UI.
- **Phasing:** **Uplift first, then features.** And specifically: **stand up the
  React foundation now** (Phase 1), not a throwaway vanilla re-skin.

### Goal of Phase 1 (this spec's implementation target)

Stand up the React/Tailwind/single-file foundation and the Brass Editorial design
system; **rebuild the questionnaire as a React app** preserving 100% of current
behaviour and its export schema; and **re-skin the matrix + exec reports** to the
same design language. Outcome: all three deliverables read as one premium offline
product, and the questionnaire is now a maintainable React app ready for Phase 2
(launcher, evidence upload, UI-triggered generation).

## 2. Locked visual design

- **Type:** Fraunces (display serif, headings) · Inter (body/UI) · JetBrains Mono
  (metadata, IDs, data). Embedded as base64 woff2 — fully offline.
- **Themes (one DNA, two skins):**
  - *Editorial Light* (default): warm paper `#f7f3ea`, card `#fffdf7`, ink `#231f1a`,
    muted `#7d7468`, hairline border `#e6decd`.
  - *Technical Dark* (toggle): warm near-black `#141216`, card `#1d1a1f`, ink
    `#ece6dc`, border `#2c2830`, subtle accent glow.
- **Accent (signature):** Brass `#9A7B32` (light) → `#D6B25A` (dark, +glow).
- **Semantic state palette (editorial-warm):** MET green `#2f6b4f` · PARTIAL ochre
  `#9a6a1e` · GAP claret `#9b2f2f` · PENDING slate `#475069` · NA grey — each with a
  soft tint for light and an alpha tint for dark.
- **Component language:** serif headlines, mono metadata, hairline rules, soft cards,
  segmented Yes/No/NA toggle, badges/pills, use-case-level evidence chips, slim
  bottom action bar (never a tall sticky pane — see §6 risks).

Tokens are defined **once** and shared (see §3) so light/dark + brass are identical
across the React app and the Python reports.

## 3. Architecture

### 3.1 The app (React) — questionnaire now, launcher later
- New Vite project (proposed dir: `app/`), **React + TypeScript + Tailwind**.
- Routes: `questionnaire` (Phase 1); `launcher` and others (Phase 2).
- **Bundle:** `vite-plugin-singlefile` → one offline `.html` with inlined JS/CSS and
  base64 fonts/assets. Opens via `file://`, **zero network requests**.
- **State:** answers / override / confidence / rationale persisted to `localStorage`
  under the existing key **`posture-assessment-record/v1`** (schema preserved).
- **Export/Import:** exports `assessment-record.json` with schema
  **`posture-assessment-record/v1`**, shape-compatible with what
  `presentation/build_exec_summary.py` and `questionnaire/roadmap_generator.py`
  consume. Import merges (don't replace).
- **Rubric (DRY):** the methodology rubric stays the single source of truth. A build
  step emits `rubric.json` (from `questionnaire/rubric_loader`) that the React app
  imports — so the 47 use cases / archetypes A0–A8 are never duplicated by hand.

### 3.2 The reports (Python) — re-skinned, not rebuilt
- `matrix/report-template.html` and `presentation/exec-summary.css` restyled to Brass
  Editorial; `brand_fonts.py` swapped to Fraunces / Inter / JetBrains Mono woff2.
- Still generated by the existing Python token-injection builds; print path preserved.

### 3.3 Shared design tokens (single source of truth)
- One `tokens` source (e.g. `design/brass-editorial.tokens.json`) drives **both**:
  (a) the Tailwind theme (app), and (b) an emitted CSS-variables file injected into
  the Python report templates. Colors/type-scale/spacing live in one place.

## 4. Phase 1 scope (decomposes into three plan-able parts)

**A. Tooling + design system**
- Vite + React + TS + Tailwind + `vite-plugin-singlefile`; offline verification
  (assert no external requests in the built file).
- `tokens.json` → Tailwind theme + emitted report CSS vars.
- Base components: Button, Badge/Pill, Card, ToggleGroup, Chip, ThemeToggle (light/dark
  with persisted preference). Embedded fonts.

**B. Questionnaire React app (uplift only — no new features)**
- Sidebar: grouped use-case nav with status dots, archetype code, search.
- Use-case view: serif title, archetype badge, mono UC id, breadcrumb.
- Ladder questions as cards with Yes/No/NA segmented toggle; A0 *bespoke* use cases as
  checkbox criteria.
- Scoring: **port `scoring.js` `deriveState()` exactly** to TS, with tests asserting
  parity against the existing fixtures.
- Override drawer: rationale (required-on-change), confidence (LOW/MED/HIGH), final
  state; "need rationale" affordance.
- Progress (X/47 + ring/bar), autosave to localStorage, JSON import/export, toast.
- Slim bottom action bar (state + Previous/Save&next) — **not** a tall sticky pane.
- **Out of scope here:** evidence upload (Phase 2). Layout leaves room for the
  use-case-level evidence row but it is not built yet.

**C. Report re-skin (Python)**
- Re-skin matrix + exec to Brass Editorial via shared tokens + new fonts.
- Regenerate `tests/fixtures/report.snapshot.html`; keep exec print path + tests.

## 6. Non-goals & risks

**Non-goals (Phase 1):** no evidence upload, no launcher, no in-browser report
generation; no change to assessment content, rubric data, scoring *semantics*, CSV
schemas, or framework data.

**Risks / mitigations:**
- *Offline bundle correctness* → automated check that the built `.html` has no
  external URLs and opens via `file://` with no network.
- *Scoring parity* → port `deriveState` with fixture-based parity tests vs the Python
  `record_state` / existing `scoring.js`.
- *Export-schema drift* → a test that feeds the React app's exported record into
  `presentation/build_exec_summary.py` and asserts it builds.
- *Sticky-pane regression* (a real v1 mockup bug) → scoring/override is normal-flow;
  only a short action bar is pinned.
- *Toolchain added to a Python repo* → document setup; keep `npm` build reproducible.
- *Matrix snapshot churn* → regenerate the frozen snapshot intentionally.
