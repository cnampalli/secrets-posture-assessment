## B. Content review

### B1. Vendor profiles (19 files, 4,069 lines total)

**Strong points:**
1. Coverage is structurally complete — every vendor has exactly 84 rows
   (37 NHI + 47 UC), no row-count drift across the cohort.
2. Tier framing in `matrix.md` §3 captures the strategic story cleanly
   (PAM = legacy lane; Fortanix = crypto-root-below-vaults).
3. The 19-vendor decision (vs original 12) is well-justified in
   `notes/decisions.md` 2026-05-22 + ADR-004; CyberArk PAM split from
   Conjur is correct given the AD-rotation entrenchment surfaced in Task 0.
4. AU residency / IRAP block is present in every profile and is summarised
   in `matrix.md` §4 — material for APRA CPS 230/234 scoping.
5. Fortanix DSM framing as "crypto root that sits BELOW vaults" is
   explicit and is reinforced in `matrix.md` §1 footnote — judges its
   apparent low NATIVE count in context, not as a competitor failure.

**Gaps / weaknesses:**
1. **Profile narrative ↔ CSV mismatch (cyberark-pam).** The end-of-table
   summary at `cyberark-pam.md:77` says "NATIVE=13, ADD-ON=11, PARTNER=3,
   GAP=13"; the actual NATIVE rows in the same table count to 10, and the
   master CSV agrees with the table (NATIVE=10). The `meta/agents.md` log
   line (row 23) copied the incorrect 13. Fix the markdown footer.
2. **Citation hygiene is uneven.** URL density (per `grep https?://`)
   ranges from `gcp-secret-manager.md=18 URLs/IC=0` and
   `cyberark-pam.md=30 URLs/IC=41` (good) to `azure-key-vault.md=0
   URLs/IC=0` and `astrix-security.md=0 URLs/IC=0` (poor — even though
   bracketed citation-key references like `[doc-2025]` exist). Vendor
   profiles that lean entirely on bracketed keys without inline URLs make
   citation spot-checking harder; the BibTeX in `meta/citations.bib`
   should be cross-checked at M3.
3. **`[INDUSTRY-CONSENSUS]` tag overuse on `aembit.md` (47), `cyberark-conjur.md`
   (47), `keyfactor.md` (48), `entro-security.md` (43).** Many of these
   could be promoted to primary-source URLs (vendor docs, vendor blogs)
   with modest additional effort.
4. **XYZ-internal attribution leaks into 2 profiles** (see §C below):
   `fortanix-dsm.md:16` directly states "XYZ migrated their Vault
   Enterprise HSM unseal from Thales SafeNet Luna → Fortanix DSM" —
   sourced from Task 0 §Q-D.04 `[INTERNAL]`. `hashicorp-vault-enterprise.md`
   contains 8 `[USER-CONFIRMED EXPERIENCE]` references (lines 12, 32,
   142, 144, 150, 154, 178, 181) that pull `[INTERNAL]` Task 0 detail
   into vendor profile narrative.
5. **Astrix's `IC=0` is anomalously low** while neighbour NHI-discovery
   profiles (Entro 43, Aembit 47, Clutch 2, Oasis 2) vary widely — the
   real driver is that astrix-security.md uses inline-prose citations
   without `[INDUSTRY-CONSENSUS]` tags; review for unsupported claims.
6. **Length asymmetry.** `clutch-security.md` (529), `venafi.md` (486),
   `keyfactor.md` (432), `azure-key-vault.md` (429) materially exceed
   prompt-03's ≤ 250-word architecture budget. Trim or split before M3.

**Unsupported claims (spot-checked, file:line):**
- `cyberark-pam.md:12` "Privilege Cloud is available in Australia via AWS
  Sydney" — `[INDUSTRY-CONSENSUS]` only; cite CyberArk's AU residency
  doc explicitly.
- `aembit.md:1` overall: 47 `[INDUSTRY-CONSENSUS]` tags + only 1 URL
  found — high tag density vs. primary-source density.
- `azure-key-vault.md` "IRAP PROTECTED assessment current" — provide the
  Microsoft trust-center URL; the profile asserts the assessment but
  carries `IC=0` and `URLs=0` per my grep, which likely means the URL is
  in a bracketed BibTeX key — confirm before M3.

**Citation hygiene (overall):** ~7 of 19 profiles carry strong URL
density (≥ 15 URLs); ~8 lean heavily on `[INDUSTRY-CONSENSUS]`; the
remainder are mixed. Estimated **fraction of claims with primary-source
URLs: 50-60 %** (rough — high variance by vendor). Acceptable for M2;
must improve for the PRD body claims at M3 (especially compliance and
AU-residency assertions).

## C. Sensitivity audit (ADR-005)

**LEAKAGE: minor — 2 vendor profiles reproduce `[INTERNAL]` Task 0
content as direct attributable claims about XYZ.**

Specifically:
- `research/vendors/fortanix-dsm.md:16-18` — "XYZ migrated their Vault
  Enterprise HSM unseal from Thales SafeNet Luna → Fortanix DSM (per XYZ
  ADR-004 2026-05-22)." Sourced from Task 0 §Q-D.04 (`[INTERNAL]`).
  Recommend paraphrasing: "A major AU Tier-1 FI migrated…" before any
  external distribution.
- `research/vendors/hashicorp-vault-enterprise.md` — 8 instances of
  `[USER-CONFIRMED EXPERIENCE]` tag carry `[INTERNAL]` Task 0 detail
  into vendor-profile narrative (Azure auth not enabled; XYZ-scale
  plugin operations; licensing churn observation). The
  `[USER-CONFIRMED EXPERIENCE]` tag is **not in the canonical tag set**
  in `prompts/README.md` invariant #2 — recommend either normalising it
  to `[USER-SUPPLIED]` and explicitly tagging the sentence sensitivity,
  or paraphrasing.

**No `[SENSITIVE]` or `[NOT-FOR-DISTRIBUTION]` content was reproduced
verbatim** in any reviewed file. `anz-current-state-evidence.md §6` and
`anz-current-state.csv` both correctly mark all rows `[INTERNAL]` and
the synthesis file's own audit confirms no `[SENSITIVE]` / `[NFD]`
content was carried in.

The 2 profile leakages above are **near-line — paraphrasing is the
right fix**; they do not by themselves rise to a BLOCK because vendor
profiles are research-tier internal artifacts that the PRD writer
controls. However, the **PRD body (M3) must use paraphrased framing**
("a major AU Tier-1 FI") rather than direct XYZ attribution from
vendor-profile bleed.
