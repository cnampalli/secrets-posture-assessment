## §9b. grill-me — adversarial interrogation (steelman → judge)

### Q1. Is reusing the PAM/secrets process-maturity archetypes (A1–A8) for IGA legitimate, or does IGA process maturity need bespoke archetypes?
**Steelman the objection.** IGA is a governance *process* discipline (campaigns, workflows, registers), not an infrastructure-deployment discipline like PAM (vaults, proxies). Forcing IGA into archetypes authored for credential lifecycle could flatten governance nuance — e.g. an access-certification campaign is not obviously the same "shape" as a privileged-account discovery sweep.
**Evidence.** The archetypes (`assessment-archetypes.csv`) are abstract control-shapes: A5 = "Inventory & Attestation," A7 = "Governance Process & Register," A8 = "Periodic Assurance Artifact," A2 = "Population Migration / Coverage." PAM uses the *identical* set the same way: PAM UC-P-014 (recertification) = A5, UC-P-017 (resilience attestation) = A8 (`pam/uc-archetype-map.csv`). IGA UC-I-005 (cert campaign) = A5, UC-I-006 (privileged sign-off) = A8. The mapping is not a stretch: a certification campaign genuinely *is* an inventory + attestation; an SoD register genuinely *is* a governance process + register.
**Judgment: LEGITIMATE.** The archetypes are domain-agnostic control-shapes, parameterised per-UC. IGA uses 6 of 8 (A7/A5/A2 ×3, A3 ×2, A8/A1 ×1) — a healthy spread, which is itself evidence the shapes fit without contortion. A bespoke IGA archetype set would be over-engineering (overcooked). **One residual gap:** A6 (Telemetry/KPI) and A4 (Lifecycle Automation) are unused by IGA, yet IGID-011 is explicitly *both a class and a KPI* and JML is lifecycle-automation-shaped — UC-I-001/003 are mapped A2 (migration) where an A4/A6 framing of the joiner/leaver SLA telemetry would arguably discriminate better. Minor. Not a rebuild.

### Q2. Is the bespoke per-area vendor-fit view *undercooked* vs the per-use-case matrix — does coarser granularity mislead a buyer?
**Steelman the objection.** The secrets/PAM domains give a per-use-case NATIVE/ADD-ON grid (fine grain). IGA collapses to 4 areas × 4 vendors = 16 cells. A buyer could read "SailPoint NATIVE on SoD" and miss that NATIVE ≠ best-in-class, or that a specific UC inside SoD (cross-system toxic-pair detection at request time) is where vendors actually differ.
**Evidence.** The coarsening is *deliberate and documented*: `iga.yaml:67` "no one suite leads every area"; the cell justifications are not one-word — they carry the discriminating detail verbatim (`iga-vendor-fit.csv` row 12: Entra SoD PARTIAL "only as access-package incompatibility … not a general cross-app toxic-combination engine … will not satisfy fine-grained cross-application/ERP-grade SoD"). The renderer preserves `justification` + `evidence_url` + `citation_keys` per cell (`report_logic.py:297-302`). The glossary defines NATIVE as "layer-relative" (`report_logic.py:39-41`).
**Judgment: RIGHT-SIZED, NOT UNDERCOOKED — with one honest caveat.** IGA capability is genuinely organised by area, not by atomic UC; SoD is correctly identified as "the discriminating column" (`RESEARCH-SUMMARY.md:190`). The verbatim justifications carry the granularity the grid lacks, so a buyer who reads the cell is not misled. **The real risk:** a buyer who reads *only the colour* (NATIVE/PARTIAL) and not the justification could conflate presence with adequacy — but that risk is identical in the per-UC matrix (NATIVE there is also presence, not efficacy). Acceptable. SHOULD-ADD a legend line reinforcing "NATIVE = capability present per the vendor's own docs, not an efficacy benchmark" at the grid head (it exists per-cell for Saviynt; promote it to the grid).

### Q3. Are the ISO unverified-by-reference citations a defensibility liability a regulator would attack, given this project's fabrication history?
**Steelman the objection.** Given a prior fabricated ISM mapping, a regulator (or the buyer's own internal audit) will treat *any* unverified citation as a credibility landmine. Three ISO controls (A.5.16, A.5.15, A.5.3) are tagged "UNVERIFIED against primary" and A.5.18 is from a secondary mirror. A hostile auditor could say "you fabricated before; how do I know these aren't fabricated too?"
**Evidence.** This is exactly the C11 red flag ("any history of a fabricated mapping … the buyer will demand provenance evidence for all of them"). The instrument's response is the *correct* one: it does NOT present these as verbatim ISO. `regulatory-trace.csv` rows 21-23 carry `framework_role=INFORMATIVE`, empty `evidence_quote`, and the control-title itself says "by reference — UNVERIFIED against primary ISO." `RESEARCH-SUMMARY.md:230-232` instructs "cite by control-ID + reference only … Do NOT present these as verbatim ISO quotes." The report renders "UNVERIFIED" (4 occurrences) — the caveat is buyer-visible, not buried.
**Judgment: NOT A LIABILITY — IT IS THE MITIGATION.** The honest move when ISO is paywalled is to mark the control informative-by-reference and withhold the quote, which is exactly what was done. A regulator attacks *concealed* weakness; disclosed weakness is defensible. The fabrication history is the reason this disclosure discipline exists, and it holds here. **MUST-FIX is narrow:** A.5.18 is still labelled BACK-MAP (row 20) with a *quoted* secondary-mirror text — it is the one ISO row that carries a verbatim quote from a non-primary source (hightable.io). For an external attestation deliverable this single row should either be re-verified against a licensed ISO copy or down-graded to INFORMATIVE like its siblings. See MUST-FIX #1.

### Q4. Is the Entra/Okta SoD = PARTIAL verdict defensible from the cited vendor docs, or opinion?
**Steelman the objection.** PARTIAL is a judgment call. A SailPoint salesperson would call Entra's SoD "NATIVE" (it ships, it's documented). Calling it PARTIAL could be read as the instrument's opinion dressed as fact — or worse, as steering toward the pure-play suites.
**Evidence.** The PARTIAL verdict is anchored to the *vendor's own constraint*, quoted: Entra `iga-vendor-fit.csv` row 12 cites learn.microsoft.com's access-package-incompatible doc — Microsoft itself scopes SoD to access-package/group incompatibility, not cross-app toxic pairs. Okta row 16 cites Okta's own doc constraining SoD to "apps with the Governance Engine enabled." The verdict rests on what the vendor documents the feature *can't* do, not on the reviewer's preference. Both pure-plays (SailPoint, Saviynt) get NATIVE on SoD from *their* docs too — so this is not steering toward one vendor; it's a capability-scope distinction (ERP-grade fine-grained cross-app SoD).
**Judgment: DEFENSIBLE, NOT OPINION.** PARTIAL is sourced to the vendor's documented scope limit. The honesty cuts both ways — Okta's verdict explicitly says it "trends toward ADD-ON where ERP-grade fine-grained SoD is in scope," disclosing the reviewer's reasoning rather than hiding it. This is the model behaviour the methodology asks for (D20). The single soft spot: Saviynt's four NATIVE verdicts rest on *marketing copy* (docs portal un-renderable) while the two PARTIAL verdicts rest on *technical docs* — an asymmetry where the pure-play gets the benefit of marketing-grade evidence and the platform players get held to their technical-doc constraints. This is disclosed verbatim ("marketing-grade source — capability presence per vendor, not an efficacy benchmark", row 6-9) but a buyer should note Saviynt's NATIVE is the softest-sourced cell in the grid. See SHOULD-ADD.

### Q5. Does excluding IGA from the cross-domain spanning map hide a real overlap (e.g. SailPoint/CyberArk identity-governance adjacency)?
**Steelman the objection.** The cross-domain concentration map exists to show a buyer where one *corporate parent* spans multiple domains (concentration risk). IGA is skipped (`build_cross_domain.py:27-33` — header-only vendor-capabilities.csv → no ranked vendors → skipped). SailPoint (IGA) and CyberArk (PAM) are both identity-security players with governance adjacency — by excluding IGA, does the map hide that a buyer standardising on, say, CyberArk for PAM and then needing IGA has a hidden adjacency/lock-in story?
**Evidence.** I checked the actual vendor sets. PAM vendors: `cyberark-pam, beyondtrust, delinea, one-identity-safeguard, teleport, wallix-bastion`. IGA vendors: `sailpoint-isc, saviynt-eic, microsoft-entra-idg, okta-oig`. The two sets are **wholly disjoint** — no shared slug, and (checked `vendor-ownership.yaml`) no shared corporate parent between an IGA vendor and a PAM/secrets vendor. The cross-domain map keys on *ultimate corporate parent* concentration (`crossdomain.build_crossmap`), not on "thematic adjacency." Because no IGA vendor shares a parent with any PAM/secrets vendor, IGA's participation would add a disjoint vendor set with `spans=1` for every parent — i.e. it would contribute *nothing* to the spanning (>=2 domains) signal the map reports.
**Judgment: NO REAL OVERLAP IS HIDDEN — the exclusion is honest and inconsequential to the map's actual signal.** The SailPoint/CyberArk "adjacency" is a *market-category* adjacency (both sell identity security), NOT a *corporate-parent concentration* (different owners) — and the map measures the latter. The exclusion is documented in code with a faithful rationale (`build_cross_domain.py:27-29`). **However**, there is a genuine, *different* gap the exclusion sidesteps: Microsoft Entra appears in IGA, and Microsoft is almost certainly a parent that spans other domains in the buyer's estate (Entra ID is foundational). If the secrets/PAM domains ever list Azure Key Vault / a Microsoft product, Microsoft *would* span — and IGA's exclusion would then hide a real Microsoft concentration. Today the sets are disjoint so it doesn't bite, but this is a latent gap to flag the moment a Microsoft secrets/PAM SKU enters another domain. See SHOULD-ADD.

**Sharpest finding (single):** Q5's latent corner — the cross-domain map's IGA exclusion is honest *today* only because the vendor sets happen to be parent-disjoint. The moment a Microsoft product (Entra is already in IGA) is listed in the secrets or PAM domain, the header-only-CSV exclusion will silently suppress a real Microsoft cross-domain concentration signal. It is a correct decision with a time-bomb assumption that is not asserted anywhere as a precondition.
